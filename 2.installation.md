# Database Installation

> **Dialect note:** This file uses **PostgreSQL** — it is the practical "install it on your machine" section. All other files in this repo use Oracle/PL-SQL syntax. (Source: p. 42 of the course PDF.)

### Running Postgres Locally with Docker
#### Explain It
Instead of installing a database engine directly on your machine, you can run it in a container via Docker. This keeps your host clean, makes the database disposable (delete and recreate at will), and is the fastest way to get a working instance for practice. The official `postgres` image starts a server listening on port 5432, and you access it through the `psql` client either from your host or from inside the container.

#### Prove It
```bash
# 1. Pull the Postgres image (once)
docker pull postgres

# 2. Run a container named postgres-db, mapping port 5432
docker run -d \
  --name postgres-db \
  -p 5432:5432 \
  -e POSTGRES_PASSWORD=YourPassword \
  postgres

# 3. Enter the container and connect as the superuser
docker exec -it postgres-db bash
psql -U postgres
```

#### Gotchas / Edge Cases
- The `POSTGRES_PASSWORD` env var sets the password for the `postgres` superuser; without it, the container refuses to start.
- Port `-p 5432:5432` fails if you already run a local Postgres on 5432 — change the host side, e.g. `-p 5433:5432`.
- Data inside the container is lost when you delete it (`docker rm`); mount a volume (`-v pgdata:/var/lib/postgresql/data`) to persist.

### Creating a User and Database
#### Explain It
Postgres separates a *role* (a login account) from a *database*. After the superuser exists, you create an application user with a password, then create a database owned by that user so the application user has full control over it. Logging in looks like `psql -U <user> -d <database>`.

#### Prove It
```sql
CREATE USER testuser WITH PASSWORD 'testpassword';
CREATE DATABASE testdb OWNER testuser;
```

```bash
# Log in as the new user to the new database
psql -U testuser -d testdb
```

#### Gotchas / Edge Cases
- `CREATE DATABASE` cannot run inside a transaction or a multi-statement block — run it standalone.
- Ownership matters: making the new user the *owner* avoids the common "permission denied for schema public" surprise.
- Oracle differs: there is no separate "user" and "database" — a schema *is* the username (see `sql-cmd.md`), and you connect to one database with `CREATE USER ... IDENTIFIED BY ...`.

### Tablespaces
#### Explain It
A tablespace is a logical storage container that maps to a physical directory on disk. You create a tablespace for a specific location (e.g. a fast SSD or a separate disk), then optionally place individual tables in it. If you create no tablespace, tables live in the default one (`pg_default`).

#### Prove It
```sql
-- directory must exist first and be empty, e.g. /var/lib/postgresql/my_tablespace
CREATE TABLESPACE bankts LOCATION '/var/lib/postgresql/my_tablespace';

-- create a table inside that tablespace
CREATE TABLE audit_log (id INTEGER, note VARCHAR(100)) TABLESPACE bankts;

DROP TABLE audit_log;
DROP TABLESPACE bankts;
```

#### Gotchas / Edge Cases
- `LOCATION` must be an absolute path; the directory must be **empty** and owned by the OS user running Postgres (`postgres`).
- Only superusers can create tablespaces.
- You cannot `DROP TABLESPACE` while it still contains objects — empty it first.
- Oracle's equivalent syntax is completely different (`CREATE TABLESPACE ... DATAFILE '...'` with extent-management clauses) — don't mix the two in an interview; this repo's other files use Oracle dialect.
