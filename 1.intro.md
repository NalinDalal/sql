# Introduction to Databases

> **Dialect note:** Oracle SQL (VARCHAR2, DUAL, connectivity examples).

### What is a Database / DBMS
#### Explain It
A database is a collection of coherent, meaningful data — "coherent" because the data must have a point of reference to make sense. To design and maintain one you must (1) decide which part of the world's data interests you, (2) identify the specific objects in it, and (3) identify relationships between those objects. A DBMS is the software that stores, retrieves, and protects that data; the benefits of using one are the classic exam list below.

#### Prove It
```sql
-- "identify objects + relationships" maps straight onto tables and FKs:
SELECT B.NAME AS BRANCH, E.FNAME AS EMPLOYEE
FROM EMP_MSTR E JOIN BRANCH_MSTR B ON B.BRANCH_NO = E.BRANCH_NO;
```

#### Gotchas / Edge Cases
- "Coherent, meaningful data" is the textbook definition — interviews contrast it with a random pile of files.
- The benefits list (reduced redundancy, no inconsistency, sharing, standards, integrity, security, data independence) is worth memorizing word-for-word; "redundancy" and "integrity" are the two most-quoted.

### Benefits of a DBMS
#### Explain It
Compared with storing data in files, a DBMS reduces data redundancy (the same fact stored several times), eliminates the inconsistencies redundancy creates, lets data be shared by many users, lets standards be set, maintains integrity (only accurate data gets in), implements security simply, and gives data independence — programs can change without the database layout changing and vice versa.

#### Prove It
```sql
-- integrity benefit in action: the CHECK rejects a bad row
CREATE TABLE ACC_TEMP (ACCT_NO VARCHAR2(10) PRIMARY KEY,
                       BALANCE NUMBER(10,2) CHECK (BALANCE >= 0));
INSERT INTO ACC_TEMP VALUES ('A1', -5);   -- ORA-02290: check constraint violated
```

#### Gotchas / Edge Cases
- "Data independence" has two flavors the interviewer may probe: *physical* (storage layout can change, queries don't) and *logical* (table structure can change, views/contracts don't) — see Rule 8/9 below and views in `advanced-sql.md`.

### RDBMS
#### Explain It
A relational DBMS stores data as related tables (relations) and is based on the relational model: rows are records, columns are attributes, and relations between tables are made through keys. The first commercial relational store was Multics Relational Data Store (1978); examples are Oracle, Microsoft SQL Server, Sybase, and IBM DB2 (Note: "EF Codd" is a common OCR typo for E. F. Codd, whose 1969-70 papers define the model and whose 12 rules follow).

#### Prove It
```sql
SELECT * FROM BRANCH_MSTR;   -- a relation: rows + columns, no ordering guarantee
```

#### Gotchas / Edge Cases
- In the relational model rows are unordered and duplicates are ideally absent — "is ORDER BY needed to guarantee order?" answer: yes, always, because table order isn't guaranteed.

### Codd's 12 Rules
#### Explain It
E. F. Codd's 12 rules define what a "real" relational DBMS should do. The exam-friendly compression: (1) all data presented as tables (Information Rule); (2) every datum addressable by table+PK+column (Guaranteed Access); (3) NULLs must be supported distinctly from empty string/zero (Systematic NULL Treatment); (4) the catalog (structure metadata) is queryable like data (Dynamic Online Catalog); (5) one comprehensive language (SQL) does DDL, DML, integrity and transactions (Comprehensive Data Sublanguage); (6) views must support manipulation like tables (View Updating); (7) set-at-a-time INSERT/UPDATE/DELETE (High-level Insert, Update, Delete); (8) physical data independence; (9) logical data independence; (10) integrity constraints via the language, notably "no NULL in a PK" and "FK values must exist as a key elsewhere" (Integrity Independence); (11) distribution independence (a distributed DB looks like a normal one); (12) no bypassing the language (Non-Subversion).

#### Prove It
```sql
-- Rule 3 in one query: NULL is a value that IS NULL, not '' and not 0
SELECT 1 FROM DUAL WHERE NULL = '';    -- no rows
SELECT 1 FROM DUAL WHERE NULL IS NULL; -- one row
-- Rule 10 in one statement: PK rejects NULL
INSERT INTO BRANCH_MSTR (BRANCH_NO, NAME) VALUES (NULL, 'x');  -- ORA-01400
```

#### Gotchas / Edge Cases
- Rules 6, 9, and 11 are admitted to be hard/failed in practice — textbooks literally say "not fully supported by any current database". Saying that shows depth.
- Rules 10-12 are the least memorized; if an interviewer asks "which of Codd's rules do real RDBMS fail?" the answer is the view-updating and independence ones.

## Normalisation

### Why Normalize
#### Explain It
Normalization reduces redundant table data to the minimum by replacing one fat table with several tables connected through relationships. The reasons are practical: simpler maintenance, faster retrieval, easier updates/inserts/deletes, fewer table restructures when requirements change, and better overall design. The technique decomposes data into two-dimensional tables, eliminates dependencies that do not fully depend on the primary key, and eliminates transitive dependencies.

#### Prove It
```sql
-- the unnormalized EmpProj idea -> three tables
CREATE TABLE PROJECT        (PROJECT_NO VARCHAR2(10) PRIMARY KEY, PROJECT_NAME VARCHAR2(40));
CREATE TABLE EMPLOYEE       (EMP_NO VARCHAR2(10) PRIMARY KEY, EMP_NAME VARCHAR2(30), RATE_CATEGORY VARCHAR2(1));
CREATE TABLE PROJECT_EMP    (PROJECT_NO VARCHAR2(10), EMP_NO VARCHAR2(10),
                             PRIMARY KEY (PROJECT_NO, EMP_NO));   -- the many-to-many link
```

#### Gotchas / Edge Cases
- Normalization is judged against *functional dependencies* — the interview keyword. Every row of a problem "is this in 2NF?" starts with listing FDs.
- Over-normalizing costs join performance; denormalization (intentional redundancy for reads) is a legitimate later step — say it if asked "is normalization always good?".

### First Normal Form (1NF)
#### Explain It
A table is in 1NF when it is a flat two-dimensional table with **no repeating groups** — each cell holds one atomic value, and every record is identifiable by a key. The procedure: take the unnormalized table, assign a primary key that uniquely identifies each record, and expand the repeating groups (the textbook EmpProj table stores "Employee number" and "Employee name" as 1-n fields inside one project row; 1NF turns each combination into its own row keyed by (Project number, Employee number)).

#### Prove It
```sql
-- The 1NF fix of EmpProj: one row per project+employee, both keyed
CREATE TABLE EMPPROJ_1NF (
  PROJECT_NO   VARCHAR2(10),
  PROJECT_NAME VARCHAR2(40),
  EMP_NO       VARCHAR2(10),
  EMP_NAME     VARCHAR2(30),
  RATE_CATEGORY VARCHAR2(1),
  HOURLY_RATE  NUMBER(8,2),
  CONSTRAINT pk_ep PRIMARY KEY (PROJECT_NO, EMP_NO)
);

SELECT PROJECT_NO, EMP_NO FROM EMPPROJ_1NF WHERE ROWNUM < 3;   -- every cell atomic, keyed rows
```

#### Gotchas / Edge Cases
- "Repeating group" = a column that holds a list (CSV, 1-n marks in one cell) — the 1NF violation to name in interviews.
- Multi-valued attributes (a person with several phones in one cell) also break 1NF; the fix is a child table.

### Second Normal Form (2NF)
#### Explain It
A table is in 2NF when it is in 1NF **and every non-key column fully depends on the whole primary key** — no *partial dependencies* on just part of a composite key. The textbook EmpProj example: "Project name" depends only on Project number, and "Employee name / Rate category / Hourly rate" depend only on Employee number, so with the composite key (Project, Employee) they are partial. The fix: remove such fields and place them in separate tables keyed by the part they depend on.

#### Prove It
```sql
-- after 2NF: three tables, nothing depends on only half a key
SELECT P.PROJECT_NAME, E.EMP_NAME
FROM PROJECT_EMP PE
JOIN PROJECT  P ON P.PROJECT_NO = PE.PROJECT_NO
JOIN EMPLOYEE E ON E.EMP_NO     = PE.EMP_NO;
```

#### Gotchas / Edge Cases
- Partial dependencies only exist with composite keys — a single-column PK is automatically in 2NF (if it's 1NF). A favorite "gotcha" question.
- The 2NF result on the textbook example splits into EmpProj(Project, Employee), Emp(Employee, name, rate), Proj(Project, name) — note the original notes had a typo listing "Employee name" inside Proj; it is *Project name*.

### Third Normal Form (3NF)
#### Explain It
A table is in 3NF when it is in 2NF and has **no transitive dependencies** — no non-key attribute depends on another non-key attribute (A → B → C means C is indirectly dependent on A through B). The textbook example: "Hourly rate" depends on "Rate category", not directly on the Employee key, so it must move to its own Rates table; the Employee row keeps only `Rate category`, and the two are linked by a foreign key.

#### Prove It
```sql
-- final 3NF schema of the textbook exercise
CREATE TABLE RATE (
  RATE_CATEGORY VARCHAR2(1) PRIMARY KEY,
  HOURLY_RATE   NUMBER(8,2)
);
ALTER TABLE EMPLOYEE ADD CONSTRAINT fk_emp_rate
  FOREIGN KEY (RATE_CATEGORY) REFERENCES RATE(RATE_CATEGORY);

SELECT E.EMP_NAME, R.HOURLY_RATE
FROM EMPLOYEE E JOIN RATE R ON R.RATE_CATEGORY = E.RATE_CATEGORY;
-- pay rates live in exactly one place; nothing is repeated per employee
```

#### Gotchas / Edge Cases
- Transitive dependency = a non-key column depending on another non-key column, "A→B→C" — cite this shape directly in interviews.
- 2NF for single-column PKs is free, so the 2NF→3NF step is where most real tables fail.

### Boyce-Codd Normal Form (BCNF)
#### Explain It
BCNF tightens 3NF: **for every functional dependency X → Y, X must be a superkey**. 3NF tolerates a dependency where X is not a superkey as long as Y is a prime attribute (part of some key); BCNF tolerates nothing — any non-superkey determinant is a violation. Whenever a table has *overlapping candidate keys* (two different minimal keys sharing a column), it often holds 3NF but fails BCNF. The textbook example: R(A, B, C) with FDs AB → C and C → B — candidate keys are AB and AC (all attributes prime, so 3NF holds), yet C → B has C as a non-superkey, violating BCNF. The familiar real-world shape is: a teacher teaches exactly one subject, students take subjects — the "Subject → Teacher" dependency must be split out.

#### Prove It
```sql
-- the "Subject -> Teacher" problem split into BCNF-clean tables
CREATE TABLE SUBJECT_TEACHER (
  SUBJECT VARCHAR2(20) PRIMARY KEY,
  TEACHER VARCHAR2(20)
);
CREATE TABLE STUDENT_SUBJECT (
  STUDENT VARCHAR2(20),
  SUBJECT VARCHAR2(20),
  PRIMARY KEY (STUDENT, SUBJECT)
);
-- every FD's left side is now a key: STUDENT_SUBJECT has key (student, subject);
-- SUBJECT_TEACHER has key (subject), making SUBJECT->TEACHER legal
SELECT S.STUDENT, T.TEACHER
FROM STUDENT_SUBJECT S JOIN SUBJECT_TEACHER T ON T.SUBJECT = S.SUBJECT;
```

#### Gotchas / Edge Cases
- "Is there a form stricter than 3NF?" — yes, BCNF — and most real-world tables in BCNF are also in 3NF; the difference only shows with multiple overlapping candidate keys.
- The classic interview comparison: 3NF eliminates transitive dependencies on non-key attributes; BCNF eliminates *every* FD whose left side is not a superkey.
- BCNF is a one-liner: "every determinant is a candidate key."

## SQL — the Language

### Features and Rules of SQL
#### Explain It
SQL (Structured Query Language) covers DML (INSERT/UPDATE/DELETE) and DDL (CREATE/ALTER/GROUPing structures), is usable by non-programmers, is **non-procedural** (you say WHAT, not HOW), is English-like, and follows a few lexical rules: statements start with a verb (SELECT, DROP), verbs take clauses (FROM, WHERE, HAVING), clauses are separated by spaces, parameters of a clause by commas, statements end with `;` (in the SQL*Plus client), and statements may span lines but keywords may not be split.

#### Prove It
```sql
-- rules in action: verb + FROM/WHERE clauses, ; terminator
SELECT NAME
FROM BRANCH_MSTR
WHERE BRANCH_NO = 'B1';
```

#### Gotchas / Edge Cases
- SQL is declarative: no loops, no branches, no "how to find the data" — that gap is exactly what PL/SQL fills (see `pl-sql.md`).
- The statement terminator is client-dependent (`;` in SQL*Plus, none needed in some APIs) — "does SQL need a semicolon?" is a client question, not a language one.

### Components of SQL: DDL, DML, DCL, DQL
#### Explain It
**DDL** (Data Definition Language) creates/modifies/deletes structures — CREATE, ALTER, DROP, TRUNCATE, COMMENT (plus GRANT/REVOKE in some classic textbooks, though these are DCL today). DDL is immediate: it implicitly COMMITs your open transaction and cannot be ROLLBACKed. **DML** changes data — INSERT, UPDATE, DELETE (plus CALL, EXPLAIN PLAN, LOCK TABLE). **DCL** controls access — GRANT, REVOKE (and COMMIT/ROLLBACK/SAVEPOINT in the old taxonomy, usually a separate TCL group today). **DQL** is the heart of SQL: SELECT, which compiles its result into a temporary result set.

#### Prove It
```sql
-- DDL: structure
CREATE TABLE DEMO_SQL (ID NUMBER PRIMARY KEY, NAME VARCHAR2(20));
-- DML: data
INSERT INTO DEMO_SQL VALUES (1, 'a');
-- DQL: query
SELECT * FROM DEMO_SQL;
-- DDL commits: the DML above survives the next statement's implicit commit
UPDATE DEMO_SQL SET NAME = 'b';
CREATE TABLE DEMO_SQL2 (ID NUMBER);        -- implicit COMMIT happens here
ROLLBACK;
SELECT NAME FROM DEMO_SQL;                 -- 'b' survived — cannot roll back anymore
```

#### Gotchas / Edge Cases
- The umlaut is DDL's lesson: any DDL statement ends your current transaction (see `transactions.md`).
- GRANT/REVOKE sit under DCL; older material lists them with DDL — either is defensible, but know both terminologies exist.
- "Which commands are DDL vs DML?" is a five-second interview filter — TRUNCATE is DDL (commits!), DELETE is DML (rollback-able).
